## Design

_task 05.04_

### Skill kinds and naming

A statement is generic when it stays true and useful copied unchanged into another repo that uses the same domain or technology. A statement is bespoke when it names a RedBooks entity, table, endpoint, page, path, environment variable, requirement id or design doc, or records a product choice the user made for RedBooks.

01. generic skills carry a plain name, such as `accounting`. Bespoke skills carry the `redbooks-` prefix, such as `redbooks-ledger`. The folder name equals the frontmatter `name`.
02. the frontmatter `description` states what the skill covers in one sentence, then a `Use when` sentence with the trigger terms an agent's task would contain.
03. examples in generic skills use neutral subjects, such as `order`, `invoice`, `Checking` and `Credit card`. Bespoke skills and RedBooks docs use hypothetical names at real Singapore institutions, such as DBS, UOB, Interactive Brokers, SP Services and Singtel. Real account names and personal details appear only in uncommitted locations.
04. generic skills link only to other generic skills, by relative path `../<skill>/SKILL.md`.
05. a lesson that mixes both kinds is split. The generic practice goes to the generic skill, and the RedBooks application goes to [Deferred to bespoke skills](#deferred-to-bespoke-skills).

**implementation decision** - the signed entry vocabulary of the **accounting rules**, where assets and income are positive and liabilities and expenses negative, is generic practice: it holds for any ledger and translates any statement through debit and credit mappings. It goes to the generic `accounting` skill. The foreign currency entry model, the cost center conventions and the HomeBudget accounts are the user's product choices, so they go to the bespoke skills.

**implementation decision** - the process skills carry the user's working conventions that recur across repos, such as the tracker pattern, the `.dev/` folder layout, log file naming and `.env` parameterization. These count as generic.

### Staged loading layout

Every skill folder follows one layout.

```
.claude/skills/<name>/
├── SKILL.md              # always-apply rules and the reference table
├── references/
│   ├── <topic>.md        # confirmed lessons and worked examples, one topic per file
│   └── open-lessons.md   # lessons to be learned, flagged as unsettled
└── templates/
    └── <file>            # copy-paste starting files, when the skill has any
```

`SKILL.md` holds, in order: the frontmatter, one paragraph on what the skill covers, `## Rules` as a numbered list, `## References` as a table of `id | file | read it when`, and `## Related skills` where it builds on another generic skill. `SKILL.md` stays under 100 lines.

A reference file opens with a one-line purpose and a `## Contents` list once it passes 50 lines. Each confirmed lesson is one `###` section headed with the lesson's title from the **lessons learned**, and written as the rule, a **why** line naming the failure it prevents, and an example. Skill files carry no lesson ids, so a skill reads cleanly on its own, and 05.CC.07 finds each lesson by its heading.

`open-lessons.md` holds one entry per lesson to be learned, with its `LT` id, a status of `open`, `experimenting` or `resolved`, the question, the evidence that would settle it and the experiment. `SKILL.md` names it with the trigger "a task touches one of the listed areas". Skill text that touches an open item carries the callout `**open lesson LT.NN**`.

**deviation** - `feature-implementation-guide` keeps its `tracker-pattern/`, `implementation/` and `validation/` subskill folders, each with a `REFERENCE.md`, and gains `open-lessons/REFERENCE.md` in the same layout. Renaming its folders would break the links in every existing tracker.

### Skills

#### 05.LA.01 accounting

`SKILL.md` rules:

01. every entry is a signed change to its account's balance, signed by its contribution to net worth: assets and income positive, liabilities and expenses negative. Entries are stored as signed amounts.
02. a transaction balances when its asset and liability entries sum to its income, expense and equity entries.
03. every entry has the sign its event gives it. A check tests each entry's sign against the event as well as the balance. Lessons: AI.05.
04. a balance follows from a reconciled balance point, an amount on a date confirmed against an independent source, plus the signed entries.
05. a transfer between the user's own accounts is neither income nor expense, and its asset and liability entries sum to zero.
06. debit and credit are translators: each statement source maps its labels or signs to signed entries.
07. amounts are exact decimals to their currency's minor unit, and a split sums exactly to its total.
08. a posted record is corrected by a reversing record and a new one, and a record that history references is retired. Lessons: LL.12.
09. sign flips for readability happen only when a statement is presented.

References:

- `accounting/references/ledger-models.md` holds LL.12. It also covers signed entries, transfers, opening balances, reconciled balance points, splits through a clearing account and billing accounts, as generic practice.
- `accounting/references/identity-assertions.md` holds LL.43. Its examples are re-derived under the signed rules, and none is copied from fs accounting-logic, per AI.01, AI.02, AI.03, AI.04 and AI.05.
- `accounting/references/statements.md` holds LL.47.
- `accounting/references/reconciliation.md` holds LL.44.
- `accounting/references/multi-currency.md` covers translation, realised and unrealised gains and statement translation mappings, as generic practice.

#### 05.LA.02 python

`SKILL.md` rules:

01. one settings object reads `.env` directly, and the app, scripts and tests all build it the same way. Nothing writes configuration into the process environment at import, and every run reports its effective mode. Lessons: LL.01, LL.04.
