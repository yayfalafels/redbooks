## 02 (closed) test strategy and cases

This tracker plans the `0.2.0` test strategy and the release-level case catalogue, defines the steps that produce them, and records the status of each task. Its two outputs are design documents: the **test strategy**, which sets how every component is proven, and the **test cases**, the starting set of cases each feature tracker copies, reconciles with its design and extends. The milestone closes when both outputs meet its closure criteria.

## Scope

This tracker plans and records the work on the **test strategy** and the release-level case catalogue in the **test cases**. The strategy sets how every part of `0.2.0` is proven to work. The catalogue turns that strategy into concrete checks, each with its trace, silo, verification layer, input and expected result. The catalogue proves every release notes section at release level. Each feature tracker then copies its cases, reconciles them with its design and adds the cases its design reveals, because full criterion-level coverage can only be known once that feature's design exists.

The strategy aims for an autonomous Claude Code agent to build, test and correct each feature through a set of test protocols, each aimed at one component and each giving a fast, deterministic pass or fail signal. A human validates the result afterwards as a secondary check, focused on the phone-layout UI, on figures only visible in the live HomeBudget app, and on the full live OAuth flow.

In scope:

01. **test protocols.** The runnable test groups, what each one exercises, what it runs against and its latency budget.
02. **run rules.** The live order, the latency budgets, the feature-scoped test sets and the settings rule.
03. **component silos.** One silo per component in the **release milestones**, each with its tools, scope, data and protocol.
04. **case selection and layers.** The rules that decide which cases get written, and the independent verification layers each case is decided by.
05. **case catalogue.** The release-level cases with their trace, silo, layer, input and expected result, and a traceability table from the **release notes** to the cases.
06. **human checklists.** A short checklist for each feature milestone with a user-visible surface.

Out of scope:

01. Test source code, case files, fixtures and stub services. The local dev and test env, schema and account 02 seed and validation utilities milestones build them, and each feature milestone extends them.
02. Test data and reference fixtures. The schema and account 02 seed milestone builds the seed, the second user and the expected-value fixtures, per its closure criteria 02 to 10.
03. Money and exchange rate assertions. The currency model milestone sets the rate precision, the stored rates and the conversion oracles, and the validation utilities milestone asserts amounts to their currency's decimal places.
04. The stub identity provider and the live provider check. The oauth login milestone builds them, per its api criteria 04 and 05.
05. Frontend test tooling and viewports. The validation utilities milestone builds the UI tester, and the local dev and test env milestone the tunnel and the emulator.
06. The agent loop. The `redbooks-deploy-and-validation-cycle` skill of the agent skills implement customization milestone names the narrowest test set for each kind of change and the triage.
07. Edge cases from the HomeBudget data review and the open design inputs. The design milestone adds and resolves them, per its closure criteria 07 and 15.
08. The final test folder layout, marker names and library versions. The repo layout and tech stack design topics fix them. Paths and markers in the **test strategy** are proposals for those topics to confirm.
09. Criterion-level coverage of each feature milestone. Each feature tracker completes it at its test cases step, per 02.CS.01.
10. Performance and load testing. `0.2.0` is a local POC with two seeded users.
11. Tests of the HomeBudget app itself. RedBooks reads the HomeBudget databases read-only, through the account `02` snapshot in `data/` and the frozen account `01` database.
12. Cloud deploy, CI/CD for the app, PDF export, S3 storage and statement reconciliation. They belong to `0.3.0` and `0.4.0`.
13. The docs publishing pipeline. The mkdocs documentation milestone validates its own build.

**closure**

- **02.CK.01** the strategy defines each component silo, its tools, its scope and the data it runs against.
- **02.CK.02** every requirement in the **release notes** maps to at least one silo, and the case catalogue has a traceability rule to follow.
- **02.CK.03** the strategy defines the case selection rules, the independent verification layers and the test run order.
- **02.CK.04** the strategy defines the live order, the latency budgets and the feature-scoped test sets of the run rules.
- **02.CC.01** the case catalogue lists every case with its requirement, silo, verification layer, input and expected result.
- **02.CC.02** every requirement in the **release notes** has at least one test case.
- **02.CC.03** every closed vocabulary value, date boundary and ownership rule named in the test strategy has a test case.
- **02.CC.04** every feature milestone with a user-visible surface has a human validation checklist.
- **02.CC.05** expected money amounts are stated exactly, to the decimal places of the currency of the account or statement they belong to.
- **02.CC.06** every accounting oracle checks each entry's sign against its event as well as the balance, and computes every check from its stated figures.
- **02.CC.07** the strategy requires every regression case to be shown to fail without its fix.
- **02.CC.08** the catalogue sets the step by which each feature milestone's tracker copies its cases, reconciles them with its design and adds the cases its design reveals, before implementation.

02.CK.01 to 02.CK.04 are the closure criteria and 02.CC.01 to 02.CC.08 the cases closure criteria of the test strategy and cases milestone in the **release milestones**, in the same order. The **test strategy** is the output that meets 02.CK.01 to 02.CK.04, and the **test cases** the output that meets 02.CC.01 to 02.CC.08.

## Design

The design content lives in the two outputs, so it can be read, audited and referenced without the planning record around it.

01. the **test strategy** holds the guiding principle, the protocols, the run rules, the component silos, the case selection rules and the verification layers, which meet 02.CK.01 to 02.CK.04. It also holds the drafts of the test data, the money and sign rules, the stub identity provider, frontend testing, the agent loop, the validation utilities and the human pass, for the milestones that own that work to confirm.
02. the **test cases** holds the open design inputs, the traceability rules and table, the case catalogue by silo, the end-to-end and environment cases, and the human validation checklists. It meets 02.CC.01 to 02.CC.08.
03. ids keep the milestone `02` prefix in both outputs, so a feature tracker or audit cites a rule or case without naming the document.

**implementation decision** - each output is edited in place by the task that owns its section, per [Implement](#implement). The tracker keeps no copy of the content, so the outputs are the one authority for it.
